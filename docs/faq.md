### 演讲备注

开场不必立即讲技术。先告诉听众：这是一个推理小说爱好者做给同好，也做给自己的长期项目。今天会回答数据、动机、技术、未来和参与方式五类问题。

## 02. OMM 到底是什么？

把分散在不同语言、不同来源中的推理小说信息，整理成一张可以探索、检索和持续完善的知识网络。它不是在线书店，也不只是书单。核心是“作品、作者、奖项、人物、系列与出版事件之间的关系”。

### 演讲备注

可以现场举例：从江户川乱步进入他的作品，再看到相关作者、奖项或角色。知识图谱的价值是把“名单”变成“关系”。

## 03. 为什么会做这个项目？

### 推理小说爱好者

希望用关系而不是榜单，发现作品、作家、流派与时代之间的线索。

### 独立开发者

从数据采集、产品设计到部署运维，完整实践一个真实产品。

### 工程经验

把测试、自动化、可观测性和长期维护带进个人项目，而不是只做 Demo。

### 验证 VectoJS

用真实复杂场景测试自研前端框架的渲染、交互、性能和兼容性。

### 演讲备注

重点强调四个动机不是彼此独立的。兴趣提供方向，独立开发提供自由度，工程经验保证质量，框架验证则让项目成为真实压力测试。

## 04. 这么多的数据来自哪里？

**开放知识**

### Wikidata · Wikipedia

人物、作品、奖项、角色、系列、国家、日期及多语言名称，是跨语言实体关系的基础。

**图书与公共领域**

### NDL · 青空文库 · Gutenberg

日本国立国会图书馆书目、日英文公共领域作品、作者与出版信息。

**奖项与行业**

### MWJ · Edgar · CWA

日本推理作家协会奖、江户川乱步奖、爱伦·坡奖、英国匕首奖等获奖与提名记录。

**中文出版语境**

### 豆瓣 · 推理罪

中文版本、译名、译者、出版社、出版日期、标签及跨语言作品线索。

**持续校准**

### 多来源交叉验证

同一事实保留来源与断言证据，通过实体对齐、规范化和去重降低错误。

**当前规模**

### 约 55 万实体

包含作者、作品版本、奖项等多种实体，并不等于 55 万部独立作品；采集库另有约 120 万条事实。

### 演讲备注

数据统计口径截至 2026-08-18：采集库 555,212 个实体、1,199,872 条事实。线上应用快照为 530,251 个实体、1,133,472 条事实。差异来自转换、清洗和应用模型筛选。OMM 后续会分别报告出版物记录、来源级作品和跨来源逻辑作品，避免把版本数当成作品数。

## 05. 全球大约有多少本推理小说？

**估计约 200 万部。**

- 狭义的推理、侦探与犯罪悬疑独立作品：约 **120 万至 220 万部**。
- 若纳入心理惊悚、间谍、法律与历史犯罪等宽口径类型：约 **200 万至 400 万部**。

主要国家和地区的估计占比：

| 国家或地区     | 占比 |
| -------------- | ---: |
| 美国           |  24% |
| 英国、爱尔兰   |  15% |
| 日本           |  14% |
| 中文地区       |  10% |
| 法语区         |   7% |
| 北欧           |   6% |
| 俄罗斯及东欧   |   5% |
| 西语、葡语地区 |   5% |
| 其他国家和地区 |  14% |

统计口径为作品的主要创作国家或文学传统；同一作品的精装、平装、电子版、再版和译本不重复计算。全球没有统一普查，因此这些数字用于介绍项目规模，不作为学术精确统计。

### 演讲备注

建议对外说“约 200 万部”，不要说成精确数字。美国、英国、日本和中文地区合计约占六成。Allen J. Hubin 的英语犯罪小说书目截至 2000 年已收录超过 10 万个标题；WIPO、ISBN 和各国出版统计还表明现代出版与数字、自出版会显著扩大记录数。若按 ISBN、译本和版本记录统计，全球可能是上千万条。

## 06. 抓到数据之后，发生了什么？

### 1. 采集与缓存

按来源限速请求，保存原始响应，支持断点续跑与问题追溯。

### 2. 规范化与对齐

统一实体、谓词、日期和名称，连接不同来源中的同一对象。

### 3. 清洗与构建

去重、聚合作品版本、保留来源证据，生成应用专用 SQLite。

### 4. 发布与服务

导入 Cloudflare D1，同时发布可校验的 R2 数据快照。

原始采集库、线上 D1、公开下载快照是三个不同层次，不是同一个文件的简单复制。

### 演讲备注

这页用于回答“爬虫是不是抓完就直接展示”。答案是否定的。真正耗费时间的是实体对齐、去重、质量审查和可追溯性。

## 09. 登录系统会带来什么？

**身份**

### 邮箱注册，用户名唯一

账号是个人数据、社区贡献与审核记录的基础，同时需要考虑隐私、找回和反滥用。

**阅读状态**

### 想读 · 在读 · 已读

每一次标记既服务个人书架，也会在匿名聚合后帮助热度与推荐系统。

**自定义标签**

### 建立自己的推理坐标系

密室、暴风雪山庄、变格、叙述性诡计、建筑诡计、短篇合集等。

**评论**

### 站内短评，长评外链

短评适合快速反馈；长评可发布在豆瓣等平台，再把链接带回作品档案。

### 演讲备注

“叙述性诡计”比“叙述性轨迹”更常见，“建筑诡计”也比“建筑轨迹”更符合推理小说语境，演示稿中已按这个表达整理。

## 10. 一本推理小说，不该只有一个分数

### 谜题逻辑

线索是否公平，推理链条是否自洽。

### 情节节奏

信息释放、悬念推进与阅读流畅度。

### 人物塑造

侦探、受害者、嫌疑人与群像是否鲜活。

### 文笔氛围

语言风格、时代感、地域与情绪营造。

### 反转惊喜

意外性与回看时的合理性是否兼具。

### 主题深度

作品是否触及社会、人性或类型边界。

默认仍提供综合评分，多维评分是可选的精细表达。

### 演讲备注

多维评分不应该提高普通用户的门槛，所以综合评分始终是默认。愿意深入评价的用户才展开多维度，这些数据也能让推荐更准确。

## 11. 第一次爬完之后，数据怎么维护？

### 从“全量爬取”转向“增量共建”

- 现有数据基数已经足够大
- 后续优先补缺、纠错和更新
- 登录后提供标准化导入模板

### 节点级反馈

- 作者姓名、国籍、日期等错误反馈
- 附带来源证据，保留修改历史
- 后台 Agent 辅助判断和修复

### 自动化审核

- 识别重复作品和重复版本
- 检查实体关系与字段冲突
- 高风险变更仍需人工确认

### 贡献即产品信号

阅读状态、标签、评分和纠错都在完善数据，也为后续推荐系统建立更可靠的依据。

### 演讲备注

Agent 自动审核不等于无条件自动写入。要保留证据、审计日志和回滚能力。涉及合并实体、删除事实等高风险操作时仍需人工确认。

## 12. 推荐系统为什么需要重做？

**目前**

### 数据库预计算推荐

主要依据静态图关系提前计算，适合作为基础能力，但缺乏真实用户反馈和个体差异。

**未来**

### 混合推荐系统

- 作品属性与知识图谱邻居
- 标签、阅读人数和热度
- 综合评分与多维评分
- 短评语义与个人阅读历史

最终目标不是“大家都喜欢什么”，而是“你下一本可能真正想读什么”。

### 演讲备注

可以解释冷启动：新用户没有阅读数据时先依赖内容、标签和热门作品；数据积累后逐渐加入个性化信号，但要避免热门作品垄断推荐结果。

## 13. 推荐机器人“相以（あい）”

### 自然语言找书

“想看一本孤岛背景、不太血腥、逻辑严密的本格推理。”

### RAG 与知识图谱

从结构化事实、标签、评价和作品邻居中检索证据，再生成可解释的推荐。

### 控制调用成本

签到与任务获得使用额度，也可通过邀请或购买补充，避免模型接口被滥用。

网页版本稳定后，可扩展为 QQ 机器人，让群聊也能直接使用。

### 演讲备注

“金币”在正式产品中可以改称“推理点数”或“线索点”，更符合产品主题。收费与邀请体系涉及合规、支付、安全和反作弊，必须晚于机器人核心价值验证。

## 14. 还有哪些可能性？

### 侦探大厅

类似 Discord 的站内聊天；如果 QQ 群已经足够方便，则不重复建设。

### 在线翻译

侧边展开翻译工具，复制外文内容后快速转换为中文。

### 热度排行榜

综合想读、已读、评分与趋势，按时间窗口生成更有意义的榜单。

### 个人推理生涯

最喜欢的侦探、作品、诡计、国家与阅读年代等个人档案。

### 作品封面

避免全量存储，考虑用户按需上传，并自动转换为 WebP 后存入对象存储。

### 持续修复

长期处理功能缺陷、UI 渲染、移动端、高 DPR、浏览器兼容和无障碍问题。

### 演讲备注

这些是候选方向而不是并行开发清单。是否开发侦探大厅取决于现有 QQ 群能否满足需求；封面功能则要先解决版权、审核和存储成本。

## 17. 技术架构是怎么样的？

**Browser**

### VectoJS 原生画布前端

技术栈：TypeScript · Bun · Vite · Canvas

单画布渲染知识图谱和界面，按需加载关系；语义层支持键盘与辅助技术。

**Edge**

### 轻量云原生 API

技术栈：Cloudflare Pages · Workers · Hono

静态前端与边缘 API 自动部署，无需维护传统常驻服务器。

**Data**

### 结构化数据流水线

技术栈：Python · SQLite · D1 · R2

采集库离线构建，线上 D1 提供查询，R2 发布带校验信息的公开快照。

### 演讲备注

“零 DOM”是指产品界面主要由 VectoJS 画布渲染，不是网页完全没有 HTML。输入、无障碍投影和页面外壳仍会使用浏览器原生能力。

## 18. 网站会不会卡？

### 不会一次画出 55 万个节点

初始只显示少量种子，用户探索时才按需加载一跳关系。搜索与图谱渲染也彼此分离。

### 真实浏览器基线

对 Chrome、Firefox、桌面、移动端、高 DPR、布局、交互和物理模拟进行自动化回归。

### 性能预算而不是主观感觉

记录帧耗时、追加节点、稳定时间、拖拽误差、碰撞与非有限坐标等指标。

### 生产体验持续监控

最近一次生产 Lighthouse：性能 99、无障碍 100、最佳实践 100、SEO 100。

### 演讲备注

不承诺任何设备上永远不卡。正确说法是：通过按需加载控制规模，通过基线测试发现退化，并针对低端设备、移动浏览器和真实数据持续优化。

## 19. 运维会不会很困难？

### 基础设施轻

Pages、Workers、D1 和 R2 由 Cloudflare 托管，减少服务器补丁、进程守护和扩容工作。

### 发布自动化

Issue、分支、测试、PR、CI、合并、部署与生产 smoke check 形成固定交付流程。

### 真正困难的是长期治理

数据质量、隐私安全、社区审核、模型费用、滥用防护和兼容性需要持续投入。

云原生降低的是机器运维，不会消除产品和社区的维护成本。

### 演讲备注

账号系统上线后，安全责任会显著增加，包括邮件验证、密码或登录凭据保护、隐私政策、数据导出与删除、风控和备份恢复。

## 20. 长期维护要考虑什么？

### 数据可信

来源、证据、去重、纠错、审核与可回滚。

### 产品可靠

测试、监控、备份、兼容性与渐进发布。

### 隐私安全

最小化收集、权限隔离、反滥用与用户控制。

### 可持续

控制云资源和模型成本，建立社区协作机制。

### 演讲备注

这是路线图里最重要但最容易被忽略的一页。功能越多，维护责任越大。宁可慢一点，也不要让数据、账号和社区治理变成不可控债务。
